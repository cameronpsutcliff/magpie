Magpie Runner

The daily AI capabilities brief

This repo collects what’s new in AI, ranks it by what builders can do with it, and publishes one Edition per Chicago calendar day.

Collectors gather Items. Magpie groups them into ranked Events, proposes testable Possibilities, and tracks Threats and Constraints that affect what builders can safely run or access.

From sources to Edition

Collectors normalize public signals into Items. The build groups Items by canonical key and ranks Events using evidence such as novelty, momentum and independent pickup.

request_json(prompt, policy, accept) tries editorial lanes in order and returns the first JSON object the caller accepts. Claude and Codex are implemented. ADR 0003 identifies local Studio or Spark endpoints as future adapters.

Edition Publication writes the dated feed and derived views. The website and Morning Brief read the published outputs.

Core domain glossary

Edition
The dated publication for one Chicago calendar day, built by the home tier, cloud tier, or backfill.
Item
A normalized observation from a collector, before grouping and editorial selection.
Event
A ranked editorial record built from one or more items associated with a canonical key.
Canonical key
The stable identity used to group observations and track the same subject across editions.
Capability
A tool, model, or development that changes what someone can build or do with AI.
Follow-up
An event about a capability an earlier edition already covered. Its editorial focus is what changed.
Library
Capabilities from earlier editions that can be recalled as partners for current arrivals.
Possibility
A proposed use of capabilities, with a recipe and a falsifiable test that could disprove it.
Ingredient
A capability used in a possibility. An earlier possibility can be referenced via builds_on.
Register
The cumulative record of constraints or threats across editions, also used to supply recent fallbacks.

Key architecture decisions

Publication and precedence

Route writes and repairs through publish(candidate) and revise(date, change) with a publication receipt. For the same Chicago date, the enriched home Edition takes precedence over a plain cloud Edition unless --force is explicit. Changes to the data/v1 layout or page IDs require a versioned migration.

Stack Fit. Python 3.12+ and the standard library keep the editorial and JSON pipeline free of external package dependencies. Thin launchers handle Git transport.

ADR 0001

Runner checkout and feed contract

magpie-runner is the authoritative operational checkout. Readers use data/v1/days/<date>.json, data/v1/rollups/<date>.json and generated page links. Schema changes require validation in schema.py and test_schema.py. The ADR calls for pytest on every PR.

ADR 0002

Edition inputs and replay

Daily runs and backfills should share build_edition(request, inputs), returning a candidate and receipt, with acquisition and publication at the edges. Replay uses sightings strictly earlier than the target date to keep novelty and follow-up flags deterministic. Editorial calls converge on request_json.

ADR 0003

The Matt Pocock engineering loop

  1. Grill with Docs. Resolve design questions against the glossary, ADRs and existing code.
  2. Spec and tickets. Define acceptance criteria and slice the work into implementation tickets that fit under 150k tokens of context.
  3. Implement and run pytest. Exercise the change and run the full suite (301-test baseline).
  4. Adversarial other-family review. Have a model from a different family challenge the implementation and its verification.
  5. Retro. Record what worked and carry lessons into the next spec.
